### 1. Hermes Tool Search — The MCP Accuracy Drop Problem (and Fix)
**Source:** MarkTechPost, NousResearch/hermes-agent · **Score:** 7/10
Hermes Agent v0.15.0 (May 29) shipped Tool Search for MCP: a deferred-schema loading pattern where the agent calls `tool_search` to find relevant tools, then `tool_describe` to load only the schemas it needs, then `tool_call` to execute. The result: Anthropic's internal MCP evals went from **49% → 74% accuracy on Opus 4** with large tool catalogs, and **85% reduction in tool-definition token overhead**. The root cause the fix addresses: when you have 34+ MCP tools exposed simultaneously, the schema overhead is ~22K tokens per turn (50% of context), which causes "decision paralysis" — the model picks wrong tools or hallucinates tool names.  
**Why it matters:** This is not a Hermes-specific problem. ANY Claude setup with multiple MCP servers hits this wall. Jarvis currently has a modest MCP footprint, but as Leo's fiction pipeline scales and adds more tool integrations (memory, RAG, chapter tracking, etc.), this becomes a real issue. The principle to apply NOW: don't expose every MCP tool in every session. Scope tool sets to the active task. The Hermes fix is a pattern Leo can build natively — defer schema loading until tool selection time.  
**Build verdict:** INFORMATIONAL — pattern is actionable as a config principle; the specific Hermes implementation is third-party code under safety gate (don't install). But: add "minimize exposed MCP tools per session" as a design rule for the fiction pipeline.

### 2. CC v2.1.161 — MCP Secrets Fix + Agent View Progress Tracking
**Source:** code.claude.com/docs/en/changelog · **Score:** 6/10
Released June 2 (after the PM run). Key changes: (1) **Security fix** — `claude mcp list/get/add` was printing secrets; `${VAR}` env references no longer expanded in output. If you've been running `claude mcp list` in any logging context, rotate any credentials that may have been exposed. (2) **Agent View improvements** — `claude agents` now shows `done/total` before the detail line when work is fanned out, plus a peek at the longest-running item. Makes parallel agent progress visible at a glance. (3) **Parallel tool calls fix** — a failed Bash command no longer cancels other tool calls in the same batch. (4) **OTEL resource attributes** — `OTEL_RESOURCE_ATTRIBUTES` values now appear as labels on metric datapoints, enabling usage metric slices by team/repo. (5) **MCP connectors** — `/mcp` collapses unused claude.ai connectors by default, reducing context noise.  
**Why it matters:** The secrets fix is the most urgent — if Jarvis or any other routine has ever logged `claude mcp list` output to disk or a file, those logs could have plain-text env var values. More useful: the `done/total` agent progress display is exactly what Leo needs when running multi-session book-writing parallel agents. Combined with the parallel tool fix, ultracode-driven workflows are now more robust on failure.  
**Build verdict:** INFORMATIONAL — changelog awareness + one security action item (rotate credentials if logged `mcp list`)

### 3. Single-Agent Beats Multi-Agent at Equal Token Budget (arxiv:2604.02460)
**Source:** arxiv.org/abs/2604.02460 (April 2026) · **Score:** 6/10
Under a fixed reasoning-token budget, single-LLM agents match or outperform multi-agent systems on multi-hop reasoning tasks. The key data: unoptimized multi-agent coordination has **515% token overhead** (6.2x the single-agent budget); even optimized multi-agent systems consume 4-15x more tokens than a single agent solving the same problem. The performance gap flips only when: (a) the task is genuinely parallelizable with no cross-context dependencies, or (b) the single agent's context would degrade below a threshold that specialist sub-agents avoid. The companion paper (arxiv:2601.04748) reinforces: skill-based single agents achieve multi-agent accuracy with **54% fewer tokens and 50% less latency**.  
**Why it matters:** This directly challenges the assumption that "more agents = better novel" for Leo's fiction pipeline. The 3W+3E+4R architecture from the Barr Group is validated for wall-clock speed (parallel chapter generation) but NOT necessarily for per-chapter quality per token spent. If the chapters are generated by 3 parallel writers, each writer is a single-agent context — and that single agent might produce better prose with the full token budget than three agents splitting it. The right design: **parallel for throughput, single-agent for quality on each independent chunk, reviewers as lightweight validators not co-creators.**  
**Build verdict:** INFORMATIONAL — academic paper with direct architectural implication for fiction pipeline design  
🔗 https://arxiv.org/abs/2604.02460  
🔗 https://arxiv.org/abs/2601.04748
