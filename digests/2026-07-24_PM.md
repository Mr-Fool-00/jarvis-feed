### 2. Cowork SharedRoot VM Escape — CVE-2026-46331 (Patched; ~500K macOS at Risk)
**Score: 7/10** · Source: The Hacker News / Accomplish AI / gbhackers · 2026-07-23 · PATCHED

**TL;DR**: A VM escape in Cowork's SharedRoot execution layer allowed a malicious Cowork skill to break out of its sandbox, read files from `/Users/<you>/`, and write to the host filesystem. ~500K macOS users affected. Patched July 22.

- **Root cause**: `act_pedit` TC action bypass in the SharedRoot container runtime — not the Claude Code layer, but the Cowork platform's VM under it
- **Exploit**: a crafted Cowork skill (`.claude/skills/`) containing a payload that abused the `act_pedit` hook before skill sandboxing engaged
- **Impact**: full read on `~/` and arbitrary write on host; no root escalation needed on macOS due to `~/Library` trust relationships
- **Fix**: Cowork now defaults to cloud execution (sandboxed remote) for all skill runs; local execution opt-in requires explicit `--local` flag
- **What you need to do**: if you ran any third-party Cowork skills between July 1-22 on macOS, treat the host as potentially compromised; rotate any secrets accessible from `~/`

**Why it matters for your stack**: Step 4.5 (never auto-install third-party skills) existed for exactly this reason. The AM digest's Cowork record-a-skill item is fine — that's first-party Anthropic. Any skills you've installed from ExcellentPrompts or other third-party sources before July 22: audit them against the CVE description and rotate secrets if in doubt.

**Build verdict**: INFORMATIONAL with action item — audit local Cowork skill installs; verify no skills ran in the vuln window; rotate `~/.anthropic` API key as a precaution.

**URL**: https://thehackernews.com/2026/07/cowork-sharedroot-vm-escape-cve-2026-46331.html

### 3. Claude Code 33K Token Overhead vs OpenCode 7K — The Real Story
**Score: 7/10** · Source: Gigazine (July 13) → HN 48883275 (July 22) → PromptZone analysis · 2026-07-22

A Gigazine benchmark showing CC's 33K baseline prompt overhead vs. OpenCode's 6.9K token baseline got traction on HN last week. The nuance that didn't make the headline:

- **CC baseline**: ~33K tokens per session open (CLAUDE.md + tool definitions + system prompt)
- **OpenCode baseline**: ~6.9K tokens (minimal system, no built-in tool definitions loaded)
- **CC cache writes**: 54× more than OpenCode in the benchmark
- **BUT**: CC's parallel tool batching means cumulative cost across a 10-task session is often within 15% of OpenCode — the cache writes pay for themselves when you're doing real multi-step work
- **When CC loses badly**: single-shot simple queries where the baseline overhead is never amortized
- **When CC wins**: multi-step agentic work (like Jarvis runs) where the system prompt is cached and tools are actually invoked

**Why it matters for your stack**: Jarvis already fits the "CC wins" profile — long runs, many tool calls, CLAUDE.md loaded once. The 33K overhead is not a concern for cron-style operation. Where it matters: if you ever build a high-frequency single-query tool on top of CC's infrastructure, the overhead profile becomes a real cost driver. OpenCode or a direct API call would be cheaper per unit there. This is a useful mental model for deciding when to use CC's full agent loop vs. a leaner client.

**Build verdict**: INFORMATIONAL — no action; current Jarvis cost profile is CC-favorable. Keep in mind for any future high-frequency single-shot use cases.

**URL**: https://news.ycombinator.com/item?id=48883275

### 4. Addy Osmani: Harness vs. Loop Engineering
**Score: 7/10** · Source: addyo.substack.com · 2026-07 (exact date unclear)

Osmani's cleanest conceptual contribution this month: a two-level vocabulary for pipeline architecture.

- **Harness** = the agent's immediate environment: which model, which tools, what permissions, what memory, what system prompt. The thing you configure.
- **Loop engineering** = the system that prompts the agent for you, one floor above the harness. The thing you build to run the harness repeatedly, with scheduling, state, escalation, and feedback.

"Own the outer loop" is his thesis: the harness is increasingly commodity (CC handles it); the value is in the loop that drives the harness — scheduling, state management, escalation logic. Jarvis is a loop. The harness is CC + MCP.

**Why it matters**: This is a useful frame for explaining what Jarvis is and what it isn't. Jarvis is loop engineering; Claude Code is the harness. When evaluating new tools: ask "is this harness or loop?" and build accordingly.

**Build verdict**: INFORMATIONAL — vocabulary, not code. Apply the frame when designing next improvements.

**URL**: https://addyo.substack.com/p/loop-harness-engineering

### 5. Addy Osmani: Long-Running Agents
**Score: 7/10** · Source: addyo.substack.com · 2026-07

Companion post to the harness/loop piece, specifically on multi-hour agent durability:

- State must survive restarts/disconnects — file-based or DB checkpoints, not in-memory
- Checkpoint granularity matters: too coarse = re-do expensive work on restart; too fine = checkpoint overhead dominates
- Fleet orchestration: when you have N long-running agents, you need a supervisor that can restart, rebalance, and detect stalls
- CC recommended for coding runs that take hours; his examples use `state/` directories (same pattern Jarvis uses)

**Why it matters**: Jarvis's `state/` directory pattern (seen.json, heartbeat, reactions) is validated by this framing. If the pipeline ever grows to multiple concurrent agents (book pipeline + digest + social), the fleet supervision pattern becomes relevant.

**Build verdict**: INFORMATIONAL — validates current architecture; keep for book pipeline design reference.

**URL**: https://addyo.substack.com/p/long-running-agents

### 6. FakeAgent: Malvertising via Real claude.ai Artifacts
**Score: 6/10** · Source: Huntress Security Blog · 2026-07-21

Huntress documented an active campaign:
- Search ads for "Claude AI assistant" → landing page → link to a real `claude.ai` Artifact (legitimate domain, TLS valid)
- The Artifact page auto-downloads a `ClaudeSetup.exe` installer → SectopRAT payload
- 29 organizations hit in the campaign window (July 14-21)
- The abuse vector: Artifacts are public, shareable, and served from `claude.ai` — no phishing domain needed

**Why it matters**: If you ever share Artifact links with non-technical users, this is the threat model they're operating in — "it's from claude.ai" no longer means "it's safe." For your own security: the attack targets downloaders, not developers, so low personal risk. For any future Leo projects sharing Artifacts with clients: warn them that claude.ai Artifacts are user-generated content, like Google Docs.

**Build verdict**: INFORMATIONAL — awareness only.

**URL**: https://www.huntress.com/blog/fakeagent-malvertising-claude-artifacts

### 8. MACE: Structured Multi-Agent Collaboration via Peer Selection
**Score: 5/10** · Source: arXiv 2607.11250 · 2026-07-13

Academic paper on why naive multi-agent LLM setups fail: agents converge to the first response without genuinely exploring alternatives (social loafing + anchor bias). MACE proposes structured peer selection — each agent is assigned specific partners to critique before synthesis, preventing convergence to the vocal agent.

The paper's insight (agents fail to explore each other) maps to the Workflow tool's adversarial verify pattern — spawning skeptic agents that are explicitly prompted to REFUTE rather than extend. Not novel for Jarvis's current architecture but validates the anti-groupthink design in the runbook.

**Build verdict**: INFORMATIONAL — validates existing workflow patterns.
