## Core Thesis

Most multi-agent systems fail not because individual agents are weak, but because **coordination is implicit**. The default approach — "give multiple agents the same goal and have them collaborate" — produces redundant work, conflicting context, and no clear escalation path.

Osmani's "orchestra" model separates two distinct roles:

### The Conductor
- Single agent. Stateful across the full task.
- Responsibilities: task decomposition, context threading, scope negotiation, conflict detection, escalation decisions.
- Never executes directly — only directs.
- Holds the global context that performers don't see.

### The Performers
- Multiple agents. Stateless within a task — each is bounded to a specific sub-problem.
- Receive a scoped prompt from the conductor, execute, return results.
- Don't see each other's work unless the conductor explicitly threads it.
- Parallelizable by default.

### The Key Insight
The conductor is NOT a bottleneck because it doesn't do the work — it makes the *decisions about* work. Bottlenecks occur when the conductor tries to understand every performer's output in detail before proceeding. Instead: conductor delegates, performers surface only what changes the conductor's next decision.

## Why This Matters for Jarvis

Leo's current Jarvis architecture is a single-agent loop: one Claude Code session that fetches, dedupes, ranks, writes, and commits. As the pipeline grows more complex (more sources, more ranking signals, more delivery channels), this hits:
1. **Context window ceiling** — 12-hour fetch results eventually can't fit in one session
2. **Fragility** — one failure in a 45-minute pipeline kills the whole run
3. **No parallelism** — fetch agents are currently spawned as background tasks but their results are still synthesized serially

A conductor/performer Jarvis v2 would look like:

```
Conductor (this session)
├── Performer: fetch-agent-anthropic  [parallel]
├── Performer: fetch-agent-github     [parallel]
├── Performer: fetch-agent-security   [parallel]
├── Performer: fetch-agent-writing    [parallel]
└── → Conductor receives structured results
    ├── Performer: deep-read-agent (top 3 candidates) [sequential]
    └── → Conductor writes digest + briefings
```

The conductor's context stays lean (just the summaries). Performers are disposable — if one fails, the conductor routes around it.

## Implementation Sketch for Jarvis

**Phase 1 (minimal):** Keep current architecture. Add explicit role declarations to fetch agent prompts:
```
You are a performer in a multi-agent pipeline. Your only job is to
fetch and surface. Return a structured JSON list of candidates — do
not rank, do not filter beyond obvious noise, do not write prose.
```

**Phase 2 (full conductor):** The main Jarvis session becomes a conductor that:
1. Spawns 4-6 fetch performers in parallel via `Agent()` calls
2. Receives JSON candidate lists from each
3. Dedupes and ranks inline (conductor context)
4. Spawns 1-2 deep-read performers for top candidates
5. Writes digest from structured results

**Key design rule from Osmani:** Performers return structured data, not prose. The conductor converts data to prose. This keeps performer prompts short and ensures the conductor's synthesis step is the only place where judgment is applied.
