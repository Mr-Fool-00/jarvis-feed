## 🔥 Top 3

### 1. IS-CoT (arxiv:2606.09709): Interleaved Structural Thinking fixes the >2,000-word generation collapse
**Source:** arxiv.org/abs/2606.09709 · **Score:** 7/10

Published June 8 2026. The paper names and quantifies what Leo has likely hit in his fiction pipeline: LLMs trained on short sequences show measurable quality collapse in long-form generation — coherence, internal consistency, and narrative structure all degrade past ~2,000 words. IS-CoT proposes embedding a structured thinking cycle **inside** generation rather than around it:

- **Plan step:** before writing each segment, generate an explicit micro-plan (what happens here, what constraints carry forward)
- **Write step:** generate the actual text segment with the micro-plan as a conditioning prefix
- **Reflect step:** after the segment, generate a brief structural audit (what was established, what changed, what must the next segment remember)

The Reflect output feeds directly into the next Plan step, creating a closed loop. Tested on 5,000–15,000 word generation tasks. Core finding: IS-CoT reduces structural inconsistency errors by **41%** and improves human-rated coherence scores by **34%** compared to straight prompting. The gains are largest on tasks >5,000 words, which is exactly where Leo's pipeline operates.

Critically: this is a **prompting protocol**, not a model change. It can be implemented as a /chapter-write skill that wraps each chapter generation in the Plan-Write-Reflect cycle. No new tools required — just a structured prompt harness around the existing generation call.

**Why it matters:** This is a direct, tested solution to the quality collapse Leo has been managing in his overnight novel runs. The Reflect→Plan loop is exactly what Jarvis's `StoryConsistencyAudit` direction (Suggestion #92) was groping toward, but IS-CoT formalizes it as an architecture rather than a post-hoc check.

**Build verdict:** BUILD IT — see briefing at `briefings/2026-06-15_is-cot-long-form-writing.md`. The Plan-Write-Reflect loop is a `/chapter-write` skill shell that can be drafted in one run. Leo approves approach → next run builds it.
🔗 https://arxiv.org/abs/2606.09709

### 2. Infini Memory (arxiv:2606.10677): Topic-structured persistent memory for long-horizon agents
**Source:** arxiv.org/abs/2606.10677 · **Score:** 6/10

Published June 9 2026. Current approaches to agent memory (dump everything in context, or flat RAG retrieval) both fail on tasks where the agent must track dozens of facts across hundreds of steps. Infini Memory proposes organizing persistent memory as **topic documents** — structured markdown files, one per topic (character, location, event, constraint), maintained and updated by the agent during task execution.

Key architecture:
- Agent maintains a **memory index** (list of topic documents + brief summaries)
- Before each generation step, agent retrieves relevant topic docs via tool call
- After each step that establishes new facts, agent writes/updates the relevant topic doc
- Benchmarked on MemoryAgentBench: **64.7% accuracy** vs. 41.3% for flat RAG baseline

The topic-document approach directly maps to what Leo's fiction pipeline would need: a `Characters.md`, `WorldRules.md`, `PlotArc.md`, and `ActiveConstraints.md` maintained per-chapter. The retrieval pattern (index → selective fetch → update after generation) is already native to Claude Code file tools.

**Why it matters:** Infini Memory is the peer-reviewed argument for what the fiction pipeline's memory layer should look like. The "topic document + iterative retrieval" pattern is more structured than the current approach and explains the 23% gap in consistency that "Lost in Stories" (PM Jun 14) found — memory retrieval wasn't topic-scoped.

**Build verdict:** INFORMATIONAL — confirms and refines the `StoryConsistencyAudit` direction. The topic-document structure is worth adopting as the memory format if Leo greenlights the consistency audit skill.
🔗 https://arxiv.org/abs/2606.10677

### 4. Bayesian-Agent (arxiv:2606.08348): agents that track which skills work via posterior updates
**Source:** arxiv.org/abs/2606.08348 · **Score:** 6/10

Published June 6 2026. Bayesian-Agent treats available skills as hypotheses and maintains a probability distribution over which skills work for which task types, updated from trajectory evidence. Instead of trying every skill or using a fixed routing table, the agent maintains a **skill posterior** that concentrates probability on skills that have succeeded in similar past contexts.

Key result: on a 20-skill agent testbed, Bayesian-Agent selects the correct skill first on 71% of trials (vs. 48% for the LLM-based routing baseline). Convergence time to stable routing drops by 4x after 50 task completions.

The practical surface for Jarvis: Leo's fiction pipeline has a growing set of skills (chapter-write, character-audit, pacing-check, consistency-check). A lightweight posterior tracker — even a simple score file per skill — would let the pipeline route tasks to skills that have historically worked rather than defaulting to the most recently defined one.

**Build verdict:** INFORMATIONAL — interesting pattern, not yet buildable without a concrete skill routing layer to attach it to. File for when the fiction pipeline skill count exceeds ~10.
🔗 https://arxiv.org/abs/2606.08348

### 5. From Failed Trajectories (arxiv:2606.06324): diagnosing harness flaws from failed execution runs
**Source:** arxiv.org/abs/2606.06324 · **Score:** 5/10

Published June 4 2026. When an agent task fails, most pipelines log the failure and move on. This paper proposes a **failure analysis protocol**: run a second agent over the failed execution trajectory to diagnose *why* the harness (CLAUDE.md, prompts, tool setup) caused the failure, and generate a patch proposal. Different from RL — this is purely diagnostic, no training involved.

Tested on 300 failed agent runs across 4 harnesses. In 64% of cases, the second-pass analysis correctly identified a patchable harness flaw (ambiguous instruction, missing tool, contradictory constraints). In 41% of cases, the generated patch was directly applicable without human editing.

**Why it matters:** Relevant to Jarvis's self-improvement loop (Suggestion #95 direction). The "second-pass failure analyst" pattern could be a Jarvis skill: after a failed overnight run, instead of just logging the error, spawn a failure-diagnosis pass to produce a patch proposal for Leo to review.

**Build verdict:** INFORMATIONAL — strong conceptual fit for Jarvis's self-improvement architecture. Adds specificity to the "harness evolution" direction.
🔗 https://arxiv.org/abs/2606.06324
