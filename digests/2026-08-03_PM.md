### 2. CC v2.1.218–219: context:fork + /code-review Subagent + DirectoryAdded Hook (July 29–30)
**Source:** github.com/anthropics/claude-code · **Score:** 8/10 · Shipped: July 29–30, 2026

Two Claude Code releases back-to-back added four substantive capabilities:

**v2.1.218 (July 29):**
- **`/code-review` as background subagent:** The command now spawns a background agent and returns focus immediately. Results arrive asynchronously. Can be chained after a build step without blocking the main loop.
- **`context: fork` in tool/skill invocations:** Copies the current full context into the spawned subagent. Previously, subagents started with a summarized or explicitly passed context. Now: fork → full shared state, no summarization loss.
- **`workflowSizeGuideline` key in settings:** Configures the default agent count target for workflow-style multi-agent runs (new per-session override mechanism).

**v2.1.219 (July 30):**
- **Claude Opus 5 as default model** in CC (replaces the previous default)
- **`DirectoryAdded` hook:** Fires whenever a new directory is created during a session. Enables scaffolding pipelines — e.g., auto-run setup when CC creates a new chapter directory.
- **Nested subagent depth 3** (was 2): Agents can now spawn agents that spawn agents, with the concurrency cap enforced across all levels.

**Why context:fork matters for multi-agent work:** Every subagent spawn is now a zero-overhead context copy. The fiction pipeline's chapter drafter → voice checker → continuity fixer chain currently passes summarized context at each handoff. With `context: fork`, each subagent starts with the full session state. This changes the architecture of parallel chapter processing fundamentally.

**Build verdict: ACTIONABLE** — context:fork is the key addition. Add to the fiction pipeline's chapter dispatch step. DirectoryAdded hook opens scaffolding automation when CC creates chapter directories. Briefing: `briefings/2026-08-03_cc-218-219-updates.md`

### 4. OrchBench: Isolating Orchestration Plan Quality via Deterministic DAG Simulation (arXiv:2607.25656)
**Source:** arXiv · **Score:** 7/10 · Published: July 28, 2026

Fresh paper (one week old) that separates orchestration failures into two independent axes: (1) **plan quality** — does the orchestrator correctly decompose the task into a valid subtask DAG? and (2) **tool reliability** — does each individual subagent execute correctly?

Prior orchestration benchmarks conflate these. A plan that works perfectly with reliable tools fails at 60% tool reliability — but that failure tells you nothing about whether the plan was bad or the tools were unreliable.

The method: replace all tool executions with a deterministic simulator that always succeeds (reliability = 1.0), measure plan quality in isolation, then sweep reliability from 1.0 to 0.5 and measure degradation curves per orchestrator.

Results on 8 orchestrators: plan quality varies dramatically even with perfect tools. High-reliability orchestrators tend to have simpler plan structures with fewer parallel branches. Anthropic models score well on plan quality but show higher variance under degraded tool reliability than comparable models.

**Build verdict: RESEARCH** — not buildable from the paper alone, but the separation is immediately diagnostic. If the fiction pipeline is failing, the framework gives you a principled way to tell whether to fix the orchestration plan (chapter dispatch logic) or the subagent implementations (drafter/checker/fixer prompts).
🔗 https://arxiv.org/abs/2607.25656

### 5. Latent Space: Felix Rieseberg on Claude Cowork — Skills vs MCP, VM-First Sandboxing
**Source:** Latent Space podcast · latent.space/p/felix-anthropic · **Score:** 7/10 · Aired: 2026 (late July per secondary sources)

Guest: Felix Rieseberg — head of Cowork at Anthropic. Built Electron at Microsoft, led the Slack desktop app.

**Skills vs MCP — the directly actionable part:**
- Skills are markdown files. No running process, no protocol handshake, no schema definition required.
- Skills are now the preferred integration path for **stateless, text-describable capabilities**.
- MCP remains correct for: authenticated services, live data, stateful connections, anything requiring a running process.
- The shift: many integrations that previously needed a full MCP server can now be expressed as a Skill with dramatically less overhead.

**VM-first sandboxing:**
- The VM is a capability unlock, not just security theater. Because Cowork runs in an isolated VM, Claude can install tools, run scripts, and work persistently without per-step user approval. The VM boundary is what makes autonomous operation safe enough to allow.
- "Guardrails by construction" — permissions are structural (folder-scoped at the VM boundary), not relying on model-instruction compliance.

**Platform strategy read** (from secondary analysis, Sakeeb Rahman Threads thread): Third-party scaffolding built on Claude's API is progressively absorbed into Cowork. The Skills mechanism commoditizes integrations that many API-layer companies sell today.

**Build verdict: INFORMATIONAL** — no immediate build, but Skills-vs-MCP framing is directly useful for any new integration decision. If adding a capability to Jarvis or the fiction pipeline: try Skill (markdown) first, reach for MCP only if you need state/auth/process.

### 6. PerspectiveGap: 14.9% Average Pass Rate on Orchestration Prompting (arXiv:2606.08878)
**Source:** arXiv · **Score:** 6/10 · Published: June 2026

Benchmark specifically testing how well frontier models respond to **orchestration prompting** — instructions passed by an orchestrator to a subagent mid-task to redirect or constrain behavior.

Findings:
- Average pass rate across all models: **14.9%** — most models frequently misinterpret or ignore orchestrator-provided context mid-task.
- Opus 4.7 notably weak on multi-hop delegation chains specifically (not globally weak, but significantly underperforms on "tell agent B to tell agent C to do X").
- Fable 5 and Opus 5 perform significantly better but still under 40%.

Implication for multi-agent pipelines: the handoff prompt from orchestrator to subagent is often the highest-failure-probability point in the chain. Debugging there before debugging the subagent's internal logic is the right order.

**Build verdict: RESEARCH** — confirms a prioritization heuristic, not directly buildable.
🔗 https://arxiv.org/abs/2606.08878
