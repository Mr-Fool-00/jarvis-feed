## What this is

The largest MCP revision since the protocol launched. The Release Candidate targets July 28, 2026 as the publication date, starting a **12-month deprecation window** for legacy servers. Deadline: ~July 28, 2027.

The Agentic AI Foundation (Anthropic, Block, OpenAI co-founded; Google, Microsoft, AWS, Cloudflare backing) now governs MCP. This spec is the first version published under that governance structure.

---

## The breaking change: stateless core

The most significant architectural change: **MCP servers can no longer rely on per-connection session state**.

The old model: client connects → server maintains a session object with per-client state → client disconnects → session cleaned up.

The new model: **plain HTTP request/response, no connection persistence**. Each MCP tool call is an independent HTTP request. The server must treat each request as if it has never seen this client before.

**What breaks**: any MCP server that:
- Stores auth tokens in connection memory (must move to request headers or external store)
- Maintains a "current working directory" or "active file" concept per connection
- Keeps conversation history in server memory
- Uses streaming that relies on a persistent connection

**What's fine**: servers that are already stateless (pure function: input → output with no side effects or persistent state).

**Migration path**: move any per-connection state to:
- Request headers (auth, context)
- External state store (Redis, database) keyed on a session token the client passes
- Or restructure as truly stateless — take all needed context in each request

## New capabilities

### MCP Apps
Servers can now return server-rendered UI components that the MCP client embeds directly in its interface. Think of it as Slack blocks but for MCP — a server can push a form, a table, a chart, or interactive controls into Claude Code or claude.ai without the user leaving the chat.

Use case: an MCP server for managing a deploy pipeline could return a confirmation UI with "Deploy to staging / Deploy to prod / Cancel" buttons directly in the CC session instead of requiring a browser context switch.

### Tasks extension
Long-running work that doesn't complete within a single tool-call timeout:
- Server starts a task, returns a task ID
- Client can poll task status (running / complete / failed)
- Client can cancel a task
- On completion, server delivers the result

No more fake-complete-then-poll hacks or streaming workarounds for multi-minute server operations.

### OAuth/OIDC authorization
Standard OAuth 2.0 / OIDC flows replace the current ad-hoc "put your API key in `~/.claude/settings.json`" pattern. Users authorize via browser redirect, tokens are managed by the client. Proper scope-limited, revocable auth.

### Enterprise-Managed Authorization (EMA) — already stable
Zero-touch SSO for organizations. Users connect to MCP servers through their existing org IDP (Okta, Azure AD, etc.) — no separate MCP consent screen. Promoted to stable this week.

## Migration checklist for Leo's MCP servers

- [ ] **Audit for session state**: list every server, identify what (if anything) each stores per connection
- [ ] **Move auth to request headers**: if any server reads auth from a connection-level variable, refactor to read from request Authorization header
- [ ] **Identify streaming dependencies**: if any server uses a persistent streaming connection for real-time updates, plan to migrate to the Tasks extension
- [ ] **Test with stateless HTTP**: spin up the new SDK RC, point your servers at it, see what breaks
- [ ] **Target migration complete before January 2027** (6 months before deadline, to leave room for edge cases)

## Context: Why this spec matters now

The Agentic AI Foundation governance means MCP is now a true multi-vendor standard, not an Anthropic proprietary protocol. Google, Microsoft, AWS, Cloudflare all have skin in the game. Anthropic will not be able to make breaking changes unilaterally. The 12-month deprecation policy is the proof of that commitment.

This also means MCP server investment is lower-risk than it was 6 months ago — you're building on a standard, not a vendor extension.
