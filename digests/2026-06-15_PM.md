### 1. AWS: Claude 4 Interleaved Thinking is IS-CoT in production
**Source:** AWS Open Source Blog + AWS VP tweet · **Score:** 7/10

Published June 13-14, 2026. AWS's Strands Agents SDK published a tutorial demonstrating Claude 4's **interleaved thinking** feature with agentic workflows. The key behavior: Claude thinks BETWEEN tool calls — not just at the start. The agent plans, calls a tool, reflects on the result, adjusts its plan, calls the next tool, and so on through the entire task — all with full extended thinking space at each step.

This is structurally identical to IS-CoT's Plan-Write-Reflect loop (from this morning's AM digest, arxiv:2606.09709). IS-CoT was described as a "prompting protocol." Interleaved thinking makes it a **native model capability**: Claude 4 already does the Plan→Write→Reflect cycle when equipped with tools + extended thinking enabled. The Strands Agents tutorial shows it concretely: no developer-defined state machine needed.

For Leo's fiction pipeline: the `/chapter-write` skill should use extended thinking (`budget_tokens: 10000`) with tool calls for `ReadFile` (gather context), `WriteFile` (generate chapter), and a `AuditChapter` tool (Reflect step). Claude 4 interleaves its thinking across these calls automatically. The IS-CoT architecture isn't a prompt trick; it's the correct way to use Claude 4 with tools.

**Why it matters:** This turns today's briefing on IS-CoT from "interesting paper, build a prompt harness" into "this is how Claude 4 already works — configure it right." The implementation is simpler than the AM digest suggested.

### 2. alexop.dev: 130-line workflow spawns 9 parallel agents with deterministic control
**Source:** alexop.dev · **Score:** 7/10

Published May 28, 2026. A practitioner built a **130-line Dynamic Workflow script** that spawns 9 parallel agents, each assigned to a different content source, collects their findings into a single ranked list, and writes a digest — completely deterministically. The control flow is code, not Claude. Only the content generation inside each `agent()` call is model-powered.

Key architecture:
- `agent(prompt, opts)` — spawns one subagent with label, model override, schema validation
- `parallel(thunks)` — runs agent tasks concurrently as a barrier (all must complete before continuing)
- Outputs are **schema-validated** (zod/JSON schema) so downstream code can rely on the structure
- The orchestrator script itself never "decides" anything — pure code logic

This is the exact pattern Jarvis uses for discovery (9 parallel source searches), and exactly what Leo's fiction pipeline needs: spawn N chapter-generation agents in parallel, each covering a different chapter of the book, all with enforced output schemas (handoff file, word count, scene checksum).

**Why it matters:** The alexop.dev script is the reference implementation for Leo's `/book-pipeline` Dynamic Workflow. The `parallel()` barrier pattern ensures chapter N+1 doesn't start until chapter N's handoff file is validated. The schema enforcement prevents silent agent failures that corrupt the pipeline.

**Build verdict: BUILDABLE** — see briefing at `briefings/2026-06-15_deterministic-orchestration.md`
🔗 https://alexop.dev/posts/claude-code-workflows-deterministic-orchestration/
