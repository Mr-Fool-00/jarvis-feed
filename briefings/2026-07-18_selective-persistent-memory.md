# Briefing: Shared Selective Persistent Memory — 4-Category Framework, 96% vs 79% Completion

**Date:** 2026-07-18  
**Score:** 8/10  
**Build_worthy:** YES  
**Category:** Agent session architecture / memory design  
**Source:** arXiv:2607.09493 · Apple Inc. · July 10, 2026  
**URL:** https://arxiv.org/abs/2607.09493

---

## What it is

Apple published an agent memory architecture study targeting exactly the problem Jarvis has: every session cold-starts with zero context from prior sessions, or (worse) tries to inject the full prior conversation history and gets confused by low-signal noise.

They tested three conditions on agentic code generation tasks:
1. **No memory** (cold start every session): 79% task completion
2. **Full history injected**: 71% task completion — *worse* than no memory
3. **Selective memory** (their approach): **96% task completion**, 14x faster per task on recurring work

The full-history condition being worse than no memory is the headline result. It validates what Jarvis's runbook already implies: don't dump 50k tokens of prior run context into a new session.

---

## The four-category framework

Apple identified exactly four types of context worth persisting between sessions:

| Category | What to keep | What to discard |
|----------|-------------|-----------------|
| **Task specifications** | Goals, constraints, success criteria | Session-specific clarifications, abandoned sub-goals |
| **Data schemas** | API shapes, file formats, DB schemas, payload structures | Specific rows/values, transient state |
| **Tool configurations** | Which tools, endpoints, auth patterns, env var names | Tool outputs, intermediate results |
| **Output constraints** | Format, length, style, downstream dependencies | Draft output, revision history |

Everything outside these four categories is discarded. The key insight: the categories define *what makes future sessions productive*, not *what happened in past sessions*.

## What this looks like for Jarvis

Right now Jarvis reconstructs its full operating context on every cron fire:
- AGENT_RUNBOOK.md (~800 lines, ~12k tokens)
- INTEREST_PROFILE.md (~200 lines, ~3k tokens)  
- SOURCES.yaml (~100 lines, ~2k tokens)
- state/seen.json (~5000 lines, ~72k tokens)
- state/reactions.md + feedback.md

The first four of these map cleanly onto the Apple categories. The issue is that the full files include a lot of static text (examples, formatting, historical context) that a selective memory snapshot could compress.

### Proposed `state/session_memory.yaml`

```yaml
# Auto-generated by Jarvis after each run. Read instead of raw config files for faster warm-start.
# Last updated: 2026-07-18T13:12:00Z

task_specification:
  role: "Jarvis Discovery Loop — AI/Claude/agent content curation for Leo"
  run_cadence: "every 12 hours (AM=00:01 UTC, PM=12:01 UTC)"
  digest_path: "digests/YYYY-MM-DD_AM|PM.md"
  slot_logic: "AM if UTC hour < 12, PM otherwise"

data_schemas:
  seen_json_format: "id -> {title, url, score, first_seen, last_seen, tags, build_worthy}"
  digest_format: "Top 3 full treatment, items 4-15 one-liners, filtered section, run meta table"
  briefing_format: "score, build_worthy, category, what it is, why for leo, implementation, scope"

tool_configuration:
  git_push: "PAT auth via remote URL override; retry 4x exponential"
  slack_delivery: "commit prefix routing (digest:, briefing:, notify:, wins:)"
  web_fetch: "blocked by proxy; WebSearch primary, WebFetch secondary"
  reddit: "blocked in CCR sandbox; skip direct API"

output_constraints:
  top3_min_score: 7
  build_worthy_max_per_run: 3
  total_items_max: 15
  briefing_requires: "score >= 7 AND build_worthy = true"
  score_drop_threshold: 3  # items below this are dropped entirely

calibration:
  last_run_utc: "2026-07-18T13:12:00Z"
  last_run_slot: "PM"
  items_seen_total: 461
  recent_top_scores:
    - id: "arxiv:2607.13071-compaction-epistemic-failure"
      score: 9
      date: "2026-07-18"
    - id: "anthropic:fable-5-permanent-july20-2026-07"
      score: 9
      date: "2026-07-18"
    - id: "arxiv:2607.05577-narrative-world-model"
      score: 8
      date: "2026-07-17"
```

The session_memory.yaml would be read first (fast, small), and only specific sections of the full files would be read when needed (e.g., seen.json only for the dedupe grep pass, not full read).

## Expected improvement for Jarvis

| Metric | Current | With session_memory.yaml |
|--------|---------|--------------------------|
| Cold-start context tokens | ~90k | ~3k |
| Time to first productive action | ~8 min (reading all files) | ~1 min |
| Run budget for content fetching | ~37 of 45 min | ~44 of 45 min |

The 14x task-time reduction Apple measured is for recurring identical tasks; Jarvis's warm-start improvement would be less dramatic but still material — the runbook is the same every run.

---

## Scope of implementation

- **Time:** 60-90 minutes to build the YAML writer (add to Step 6.5 of the runbook) and update Step 0 to read session_memory.yaml first
- **Risk:** Low — additive. Existing reads remain as fallback if session_memory.yaml is absent or stale
- **Dependencies:** `state/seen.json` must still be read for deduplication; this just replaces the config-file reads with a cached summary
- **Leo confirmation required:** Yes — minor runbook change + new state file
