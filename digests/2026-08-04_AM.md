### 2. Claude Code Token Optimization: 19 Changes (Build to Launch, Aug 2026)
**Source:** Build to Launch Substack · **Score:** 7/10 · Published: Aug 2026 · ACTIONABLE → briefing: `briefings/2026-08-04_cc-cost-management.md`

A synthesis Substack post cataloguing 19 concrete CC configuration changes and prompting adjustments the community has tested for reducing per-session token consumption. Published directly in response to the Sonnet 5 Sept 1 pricing announcement.

**Highlights from the list:**
- **`/compact` threshold:** Default triggers at context ~75% — override to 50% to compress earlier and reduce expensive tail-of-context reads
- **CLAUDE.md pruning:** Every byte in CLAUDE.md appears in every context window. The author demonstrates that reducing CLAUDE.md from 4KB to 1.2KB (removing verbose explanations, keeping only directives) cuts per-session input tokens by ~8% on long sessions
- **Haiku 4.5 for mechanical subagents:** Routing file-scanning, glob-matching, and format-validation subagent steps to Haiku 4.5 instead of Sonnet 5 cuts those steps to ~5% of the cost with no quality loss
- **`output_tokens` budget per step:** Setting explicit max-output-tokens per subagent task (rather than leaving it uncapped) prevents verbose agents from running up large output bills
- **Prompt caching awareness:** CC automatically caches the system prompt + CLAUDE.md, but only when the session is long enough to hit the cache threshold. Starting a fresh session for every 5-minute task never benefits from caching; batching related work into a single long session saves significantly at volume
- **Context window budget flag:** `--max-context-tokens` (experimental as of v2.1.219) hard-limits context size; useful for parallel agents that don't need full shared state

**Why it matters now:** Sept 1 is 28 days away. These techniques are directly applicable to Jarvis's own token budget. Briefing covers actionable changes to implement this week.

### 3. Claude Code Usage Limits Playbook 2026 (Developers Digest, Aug 2026)
**Source:** Developers Digest · **Score:** 7/10 · Published: Aug 2026 · ACTIONABLE → combined in: `briefings/2026-08-04_cc-cost-management.md`

A companion guide to item 2, focused specifically on CC's **usage limit system** (distinct from API token costs). Key insight: CC's per-session usage limits treat Opus 5 as consuming **5× the budget** of Sonnet 5, and Haiku 4.5 as consuming **~0.2× the budget**. This is independent of what you pay per token — it's a separate rate limit layer on CC subscriptions (Max, Pro, Team).

**Playbook structure:**
- **Understand the two meters:** API token cost (what you pay) vs. CC usage allowance (rate limit). Most users conflate them; they're separate.
- **Model tier budget math:** 1 Opus 5 call ≈ 5 Sonnet 5 calls ≈ 25 Haiku 4.5 calls from a usage-limit perspective
- **Strategies when approaching limits:**
  - Switch the CC default model mid-session (`/model sonnet-5`) — CC continues the session on the cheaper tier without losing context
  - Use `--resume` to pick up a previous session without re-burning context on preamble
  - Delegate to API (non-CC) for high-volume batch work; save CC sessions for interactive/complex tasks
- **Organization-level controls:** On Team tier, admins can set per-user model locks via the admin console — prevents individual contributors from accidentally burning shared Opus 5 budget on mechanical tasks

**Why it's paired with item 2:** The playbook addresses the limit layer; the Substack post addresses the token-cost layer. They're complementary: reducing token consumption (item 2) helps API cost; managing model tiers (item 3) helps CC subscription longevity. Both matter before Sept 1.

### 4. SkillOS: Learning Skill Curation for Self-Evolving Agents (arXiv:2605.06614)
**Source:** arXiv · **Score:** 6/10 · Published: May 2026 (catching up this window)

Paper proposing a framework for agents to build and prune their own skill libraries over time — identifying which capabilities they actually use vs. accumulate-and-never-invoke, and automatically surfacing high-value skills to a "working memory" layer while archiving low-use ones.

The mechanism: each skill invocation is logged with task context and outcome. A background curator agent (lower capability, lower cost) periodically reviews the log, promotes skills with high success correlation, demotes rarely-invoked or low-success skills, and suggests new skills based on patterns of "things the agent attempted manually that a skill would have handled."

**Why it's relevant:** Jarvis's skill library grows with every briefing, but there's no curation mechanism. Skills added in April for the fiction-pipeline scaffolding phase are still present even if never invoked since May. A lightweight version of SkillOS's curation loop could flag unused Jarvis skills for review.

### 5. MACA: Multi-Agent Coordination Adaptation via Structure-Guided Orchestration (arXiv:2605.25746)
**Source:** arXiv · **Score:** 6/10 · Published: May 2026 (catching up this window)

Paper introducing a dynamic orchestration method that adapts the agent coordination structure (static pipeline → branching → full DAG) based on mid-task complexity signals, rather than committing to a fixed topology at task start.

The key result: tasks where the required structure isn't known in advance (common in open-ended research or writing tasks) show 23% lower total token cost and 18% higher success rates when MACA's adaptive coordinator is used vs. a fixed-topology orchestrator. The adaptive cost isn't free — the coordinator itself adds ~8% overhead — but the net saving is positive on tasks above a certain complexity threshold.

**Relevance to fiction pipeline:** The chapter-drafting pipeline commits to a fixed parallel topology (all chapters drafted concurrently, then reviewed). MACA suggests that for chapters with unusually complex dependencies (flashbacks, POV shifts, timeline nonlinearity), a sequential-with-verification topology outperforms the default parallel approach. The paper provides a simple complexity classifier that could gate topology selection.

**Build verdict: RESEARCH** — interesting framing for the fiction pipeline, but implementing the adaptive coordinator is a significant undertaking. File for future pipeline architecture review.

🔗 https://arxiv.org/abs/2605.25746
