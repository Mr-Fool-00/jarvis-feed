### 2. Blackboard Architecture for Multi-Agent Pipelines — No More Serial Context Passing (arXiv:2507.01701)
**Source:** arXiv · **Score:** 8/10 · **⭐ BUILD-WORTHY — briefing in #improvements**

Researchers at CMU + Stanford propose a **shared-state "blackboard" document** as the coordination primitive for multi-agent systems. Instead of each agent passing its full context to the next in a serial chain, all agents read and write to a single structured document — like a whiteboard in a team room. The key insight: the bottleneck in multi-agent pipelines is usually the inter-agent context handoff (the prompt you have to craft to tell agent B everything agent A learned), not the agents themselves.

**Architecture:**
- A JSON/Markdown document (the "blackboard") that all agents read from and write to
- Agents declare: what they read from the blackboard, what they write back
- An orchestrator coordinates which agents run in which order but doesn't carry content — just names
- The blackboard holds all story state (characters, plot decisions, world facts, unresolved threads) across the entire pipeline

**Benchmark results:** 12–31% reduction in plot contradiction rate vs. serial chaining across two long-form fiction generation benchmarks. The win comes specifically from eliminating the "game of telephone" problem where each agent in a chain has a slightly different understanding of what happened before.

**Concrete fit for Leo's fiction pipeline:** This is directly applicable. Leo's current pipeline passes context linearly (research agent → outline agent → prose agent). Each handoff compresses and mutates what came before. The blackboard pattern would mean the outline agent writes to a shared document, the prose agent reads from the same document, and Leo can inspect/edit the shared state at any point. A Jarvis-built implementation could be as simple as a structured Markdown file that all CC sub-agents read/write with explicit section contracts.

🔗 https://arxiv.org/abs/2507.01701

**Build verdict:** BUILD-WORTHY — full briefing committed separately. Core idea is implementable as a Jarvis skill within 1–2 sessions. See `briefings/2026-07-02_blackboard-multiagent.md`.

### 5. TOKI: Bitemporal Contradiction Resolution for Agent Memory (arXiv:2606.06240)
**Source:** arXiv · **Score:** 7/10

TOKI introduces a **bitemporal memory architecture** for long-running AI agents: each memory entry carries both when it was true in the story world (story time) and when the agent recorded it (system time). When a story revision creates a contradiction (Chapter 12 says the character has a scar; you revised Chapter 4 to remove the injury that caused it), TOKI detects the inconsistency by comparing bitemporal windows and flags it for resolution before it propagates.

The key insight: most agent memory systems track only system time, which means they can't distinguish "this was updated because the story changed" from "this was recorded incorrectly and needs correction." Bitemporal indexing separates these cases cleanly.

**Fiction pipeline relevance:** Directly applicable to Leo's long-form manuscript work. The pattern could be implemented as a thin layer on top of the existing `CONTEXT.md` pattern — each fact entry gets `[as-of-chapter: N]` and `[recorded: <date>]` fields, and a validation pass checks for temporal contradictions before the prose agent runs.

🔗 https://arxiv.org/abs/2606.06240

Build verdict: INFORMATIONAL — worth tracking alongside Blackboard (Item 2). Not build-worthy independently; better as a component of a larger memory system.

### 7. MCP July 28 RC: Explicit-Handle Pattern + Tasks Extension
**Source:** spec.modelcontextprotocol.io · MCP GitHub · HN · **Score:** 7/10

The July 28 release candidate formalizes two changes:

**Explicit-handle pattern:** Session pinning is out. Clients now pass an explicit session handle (`X-MCP-Session` header) in each request rather than relying on server-side session state. This makes MCP servers stateless by default — better for horizontal scaling, better for failover. Existing session-pinned code will need a migration to match handle-passing semantics.

**Tasks extension:** New async work primitives — `tasks/create`, `tasks/status`, `tasks/cancel` — analogous to `Promise` but for cross-agent async work. A client can create a task, get a task ID, and poll or subscribe for completion. This is the missing primitive for the "fire a long-running tool call and come back later" pattern.

**Impact on Jarvis:** The discovery loop itself is stateless (no MCP session state between runs), so no migration needed for current Jarvis infrastructure. The Tasks extension is directly relevant to future Jarvis features (e.g., kick off a deep-dive research task and continue the run while it completes).

🔗 https://spec.modelcontextprotocol.io/changelog/2026-07-28-rc

### 11. StoryBox: Character Simulation Before Prose Generation (arXiv:2510.11618)
**Source:** arXiv · **Score:** 6/10

StoryBox proposes **running character simulation passes before prose generation**: before writing any prose, a simulation agent plays through the scene as each character in turn, producing a "character decision log" (what would this character want? what would they do? what do they know?). The prose generation agent then writes from the character decision log rather than from the outline alone.

**Why this matters:** The most common failure mode in AI-generated fiction is "characters do what the plot needs" rather than "characters do what they'd do." StoryBox's pre-simulation pass forces the model to reason from character motivation first, which reduces plot-convenient inconsistencies.

**Benchmark:** 18% improvement in human-rated character coherence on FictionBench across 500-page novel sections (n=40 evaluations). Comparable quality improvement to having a dedicated character editor review each chapter.

🔗 https://arxiv.org/abs/2510.11618

Build verdict: INFORMATIONAL — relevant to fiction pipeline. Pairs well with TOKI (Item 5) and Blackboard (Item 2) for a coherent memory+character architecture.

### 12. Writer-R1: Memory-Augmented Replay for Style Consistency (arXiv:2603.15061)
**Source:** arXiv · **Score:** 6/10

Writer-R1 addresses **style drift** in long documents: the phenomenon where a model's prose voice shifts between the beginning and end of a long-form piece. The approach: train a lightweight "style retrieval" head on the author's existing text, then during generation, retrieve and replay style-relevant passages as implicit context injections.

The practical implication for Leo's use case: you don't need to train anything. The same principle can be implemented with a retrieval step — before each new chapter, retrieve the 3–5 most stylistically similar passages from the existing manuscript and include them in the prose agent's context. The author's own voice from earlier chapters becomes the style guide.

**Result:** 23% reduction in style inconsistency scores on the AuthorBench benchmark vs. generation without retrieval.

🔗 https://arxiv.org/abs/2603.15061

Build verdict: INFORMATIONAL — low-effort to prototype as a Jarvis skill. Would require a small embedding/retrieval layer. Not build-worthy independently; best evaluated after Blackboard architecture is in place.

### 14. "Remember the Decision, Not the Description" — Compressed Memory for Long Documents (arXiv:2605.10870)
**Source:** arXiv · **Score:** 5/10

This paper argues that most agent memory systems store too much: they compress full descriptions of events into shorter summaries, but the summaries still carry irrelevant detail. The proposed alternative: store **only the decision** (what action was taken) and **the constraint** (what rule or value drove it), discarding the narrative description entirely.

Example: instead of "The character decided not to reveal the secret because they were afraid of how their sister would react, given her history of overreacting to surprises," store: `[decision: withheld secret] [constraint: protect sister's emotional state]`.

The resulting memory traces are 10x smaller and 40% more reliably retrieved when the relevant constraint appears again in a new scene.

🔗 https://arxiv.org/abs/2605.10870

Build verdict: INFORMATIONAL — complementary to TOKI (Item 5). The compression format is simple enough to implement as a Jarvis pre-processing step.

### 15. EMBER: Selective Memory Retention for Persistent Agents (arXiv:2606.05894)
**Source:** arXiv · **Score:** 5/10

EMBER proposes a **salience-based memory retention** system for agents that run across many sessions: instead of retaining all memories equally, EMBER scores each memory at write time by predicted future utility (based on how often similar memories were retrieved in the past). Low-salience memories are automatically archived after N sessions; high-salience memories are kept in the active retrieval pool indefinitely.

The result is a memory system that grows sub-linearly in size even as the agent accumulates experience — useful for persistent agents like Jarvis that run twice-daily over months.

**Relevance to Jarvis:** `state/seen.json` already has a manual 30-day pruning window. EMBER's approach would add a usage-signal dimension: items that were ranked high AND matched Leo's feedback reactions would get extended retention; items that were filtered but kept around anyway would be pruned faster.

🔗 https://arxiv.org/abs/2606.05894

Build verdict: INFORMATIONAL — interesting direction for `seen.json` evolution. Not build-worthy on its own yet.
