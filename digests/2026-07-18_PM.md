### 1. arxiv:2607.13071 — Compaction as Epistemic Failure: How CC Fabricates Confirmed Results from Killed Processes `arxiv:2607.13071-compaction-epistemic-failure` · Score: 9/10 🔥

**Source:** arXiv (cs.SE) · Hiroki Tamba (independent) · July 11, 2026  
**Why it matters:** Tamba documents a real production failure: a database sync process was silently broken for 20 days because Claude Code's compaction summary captured partial stdout from a timed-out command (exit code 143) and narrated it as a confirmed result. The next session loaded the summary, saw "sync completed," and continued on a false foundation. The paper proves the failure mode exists across CC model versions.

The mechanism: when a command times out mid-execution, CC captures whatever appeared on stdout before the kill signal. The compaction summarizer — which doesn't receive exit codes, only text — generates natural language that conflates "appeared on screen" with "succeeded." Subsequent sessions inherit the fabricated confirmation as ground truth.

The fix the paper recommends: compaction prompts must explicitly include exit codes and distinguish "last observed state" from "confirmed durable outcome." Storage operations need post-compaction re-verification hooks.

**Leo relevance:** Jarvis runs multi-hour CC sessions with periodic compaction. Any Bash tool call that approaches the 2-minute timeout — particularly `git push`, `curl` to Slack webhooks, or `npm` install operations — can produce a compacted "success" that's actually a kill. The `state/failures.log` write is a partial mitigation but doesn't survive if the write itself is what was killed. Buildable mitigation: add explicit exit-code capture to every Bash call in the runbook.

**Build_worthy:** YES — see briefing. The exit-code wrapper pattern is a 20-line CLAUDE.md addition.

🔗 https://arxiv.org/abs/2607.13071

### 3. arxiv:2607.09493 — Shared Selective Persistent Memory: 96% vs 79% Completion, 14x Faster (Apple) `arxiv:2607.09493-shared-selective-memory-apple` · Score: 8/10 🔥

**Source:** arXiv (cs.AI) · Apple Inc. · July 10, 2026  
**Why it matters:** Addresses the cold-start problem in multi-turn agentic code generation. Each new session discards the configuration choices, domain constraints, schema knowledge, and tool patterns that made previous sessions productive. The naïve fix — persist full conversation history — actually degrades quality because models weight recent low-signal chatter above older high-signal guidance.

Apple's solution: identify and retain exactly **four categories** of reusable context, while discarding everything else:
1. **Task specifications** — what the agent is supposed to do (goals, constraints)
2. **Data schemas** — the shape of inputs/outputs (API signatures, file formats, DB schemas)
3. **Tool configurations** — which tools to use and how (MCP endpoints, env vars, auth patterns)
4. **Output constraints** — format, length, style, downstream dependencies

Results on agentic code generation: 96% task completion vs 79% (no memory) and 71% (full history). The full-history condition being *worse* than no memory is the key finding — it validates selective retention over naive persistence. 14x task-time reduction via zero-token warm-start for recurring tasks.

**Leo relevance:** This maps directly onto Jarvis's session architecture. Right now Jarvis reconstructs its full operating context — runbook, interest profile, seen.json, feedback.md — from scratch on every cron fire. A selective-memory layer storing just (1) the current AGENT_RUNBOOK digest, (2) SOURCES.yaml fingerprint, (3) tool config snapshot, and (4) the last-run scoring calibration would let Jarvis cold-start in under 1k tokens vs the current 20k+ token cold-start.

**Build_worthy:** YES — see briefing. The four-category taxonomy is an immediate YAML schema for a `state/session_memory.yaml` file.

🔗 https://arxiv.org/abs/2607.09493

### 6. arxiv:2607.12747 — OAT: Unsupervised Failure Attribution from Successful Trajectories `arxiv:2607.12747-oat-tracing-agentic-failure` · Score: 7/10

**Source:** arXiv (cs.AI) · UW–Madison + Microsoft Research · July 14, 2026  
Trains exclusively on successful agent trajectories (no error labels needed), then at inference identifies which steps deviated from the success distribution in a failure run. Uses Neural Controlled Differential Equations to model the trajectory as a continuous latent path — any step with anomalous latent dynamics is flagged as the failure point. Practical upshot: zero labeled failure data needed to bootstrap an agent debugger. Cheap to add to any existing CC pipeline.

🔗 https://arxiv.org/abs/2607.12747
