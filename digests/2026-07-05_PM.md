### 3. PROJECTMEM: Event-Sourced Memory-as-Governance for AI Coding Agents · arXiv · 8/10

**Source:** arXiv:2606.12329 (June 2026, surfaced July 5 in weekly arXiv scan)

**What it is.** PROJECTMEM treats each coding session as an append-only event log of typed events: `issue`, `attempt`, `fix`, `decision`, `note`. That log is deterministically projected into compact, AI-readable summaries served via MCP. The key architectural novelty: a **pre-action gate** that warns the agent *before* it does something it's already failed at in this or a prior session.

**The Memory-as-Governance pattern.** Before the agent edits a file, a pre-action check asks: "Have you tried this exact approach before? Did it fail? Is this a known-fragile file?" If yes — the gate surfaces that history as context before the agent proceeds. This prevents the failure loop where an agent attempts the same wrong fix 3-4 times in a row because it has no persistent record of prior attempts.

**Ship details.** 3-dependency Python package. 14 MCP tools, 19 CLI commands. Verified working: Claude Desktop, Cursor, Antigravity, Codex. 100% local, no cloud, MIT license. Two-month dogfooding study: 207 events across 10 real projects.

**Application to your fiction pipeline (direct remapping):**
- `issue` events → unresolved plot holes or character inconsistencies flagged in session
- `attempt` events → revision approaches tried ("tried making the confrontation scene work as a dialogue — felt false")
- `fix` events → what resolved the issue
- `decision` events → authorial choices locked in ("keeping Chapter 3 in third-person limited")
- Pre-action gate → before generating a scene, check whether this approach already failed in a prior session

**Safety gate note.** Third-party code — Step 4.5 applies. Do not install without Leo's review. But the pattern is immediately buildable natively: the event-sourced log structure and pre-action gate can be implemented as a Jarvis skill without adopting the third-party library.

### 4. Simon Willison: "Better Models: Worse Tools" — API Schema Adherence Regression · Simon Willison · 7/10

**Source:** simonwillison.net, July 4, 2026 — ["Better Models: Worse Tools"](https://simonwillison.net/2026/Jul/4/better-models-worse-tools/)

**The finding.** Opus 4.8 and Sonnet 5 (the two models you're running in CC daily) are calling tool APIs with **invented extra fields** that don't match the declared JSON schema. Willison's specific example: Pi's edit tool, where the model adds fields in nested arrays that were never defined. The model is "helpfully" extending the schema rather than adhering to it.

**Why this affects your stack.** If you're calling MCP tools or custom tool APIs in any Jarvis or fiction pipeline skills, both Opus 4.8 and Sonnet 5 may be silently adding spurious fields to tool calls. Depending on how your tools parse input (strict vs. permissive), this can cause:
- Silent schema validation failures that return no output instead of an error
- Unexpected downstream behavior if the spurious fields are passed through
- Debugging dead ends ("why did this return nothing?")

**The diagnosis Willison gives.** He calls it "smarter but more opinionated" — newer models internalize richer intent about what a tool *should* do and over-extend the schema based on that intent. The fix is not obvious: you can add schema validation with strict `additionalProperties: false`, but that causes the model to retry repeatedly as it invents different extensions.

**Action for your pipeline.** For each MCP tool or skill you're using that takes structured input: test with Opus 4.8 and Sonnet 5 specifically. Add `additionalProperties: false` to tool schemas where you want strict adherence. Log tool calls at the raw level to catch spurious fields before they cause silent failures.
