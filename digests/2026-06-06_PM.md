### 1. CC v2.1.166: `fallbackModel` setting + thinking control + cross-session security hardening
**Source:** code.claude.com/docs/en/changelog · **Score:** 7/10
**Build verdict: INFORMATIONAL — apply `fallbackModel` to settings.json today**

Three genuinely useful things landed in one release. **First:** `fallbackModel` setting in `.claude/settings.json` lets you configure up to three fallback models tried in order when the primary is overloaded or unavailable. This is quietly huge for any long-running pipeline — if Opus 4.8 throttles mid-chapter-run, the pipeline automatically falls back to Sonnet instead of dying. **Second:** `MAX_THINKING_TOKENS=0`, `--thinking disabled`, and per-model thinking toggles now disable thinking on models that think by default. Combined with `/effort`, you now have real per-session cost controls that didn't exist before this release. **Third:** relayed messages from other Claude sessions no longer carry user authority — a security hardening specifically for multi-agent setups where agents talk to each other.

Also ships: JetBrains IDE terminal flickering fixed (IntelliJ, PyCharm, WebStorm on 2026.1+), Windows PowerShell validation hang fixed, background agent git worktree issues fixed.

**Why it matters:** Add `"fallbackModel": ["claude-sonnet-4-6", "claude-haiku-4-5"]` to your `.claude/settings.json` before you spin up a multi-chapter book run. The cross-session authority change is load-bearing for any of your multi-agent setups where sessions relay messages to each other — the security model is now tighter by default. And `--thinking disabled` finally gives you a clean way to run fast/cheap passes (outlining, continuity checks) without the overhead of extended thinking.

🔗 https://code.claude.com/docs/en/changelog

### 2. SWE-Skills-Bench: 80% of Agent Skills Produce Zero Improvement
**Source:** arxiv.org/abs/2603.15401 · **Score:** 7/10
**Build verdict: INFORMATIONAL — critical input to how you design your skill library**

First controlled benchmark measuring whether agent skills actually help on real tasks. 49 public SWE skills, 565 task instances from authentic GitHub repos with acceptance criteria, deterministic pass/fail verification. Results: **39 of 49 skills (80%) yield zero pass-rate improvement.** Average gain across all 49: +1.2%. Token overhead: up to +451% on tasks where pass rates didn't move. Only 7 skills produced meaningful gains (up to +30%). Three skills actively degraded performance (up to -10%) due to version-mismatched guidance conflicting with project context.

The key insight buried in the methodology: skills that work are narrow, specialized, and well-matched to task context. Skills that don't work are generic, multi-purpose, or contain stale guidance that contradicts the live repo.

**Why it matters:** Before you build out a 10-skill `/book-pipeline`, this is the calibration input. The conventional wisdom is "more skills = more capable Claude." This paper says the opposite: most skills are noise, some are actively harmful, and the few that work are the narrow precise ones. Apply to your fiction stack: one tight voice-DNA skill, one tight continuity-check skill, zero generic "writing tips" skills. The paper is SWE-focused, but the finding (skill quality > skill quantity, narrow > broad) translates directly.

🔗 https://arxiv.org/abs/2603.15401

### 3. Simon Willison → Charity Majors: "AI enthusiasts vs skeptics — one races time, one races entropy"
**Source:** simonwillison.net/2026/Jun/4 → charity.wtf · **Score:** 6/10
**Build verdict: INFORMATIONAL — useful mental model for Leo's own AI-heavy workflow design**

Charity Majors (Honeycomb, formerly Parse/FB infra) wrote the original piece; Willison linked/surfaced it. The core frame: AI enthusiasts point to "real, non-imaginary, discontinuous leaps in capabilities from teams that lean in hard" and warn that teams sitting it out could be out of business. AI skeptics worry that "when you ship code faster than engineers can read it in domains where nobody has full context, you make withdrawals from a trust account that took years to build — reliability degrades and institutional knowledge evaporates." The kicker from Willison: **there's no natural feedback loop connecting the two groups in the same org**. Designing those feedback loops (where enthusiasts and skeptics actually share the same evidence) is the real organizational design problem.

**Why it matters:** The "no feedback loop" insight translates directly to Leo's book pipeline. Right now the feedback from reading your own novel chapters is informal. A structured quality gate (agent reviewers who surface problems back to the writer agents before the chapter is committed) is exactly the feedback loop Majors and Willison are describing — but built into the pipeline, not left to informal human review. The paper architecture lesson from item #2 and the feedback loop framing from this item are pointing at the same design principle.
